### What was built

1. **Buttons page copy fix in `docs/design.html`**: every button label across the Sizes and States grids now just reads "Button" (was a mix of "Request Info"/"Continue"/"Delete" etc.) — direct instruction, mechanical change, no design implications.
2. **Google SSO button rebuilt with the real Google mark**: replaced the plain `Button`-atom "Continue with Google" with a purpose-built button using Google's actual 4-color "G" logo (inline SVG, the standard open-source path data) — Google's own branding guidelines require the real mark, not a generic icon. Styled as a white/bordered pill (reusing `surface`/`border`/`text-primary` — no new tokens) since Google's button spec doesn't fit any of the doc's 4 button variants; documented as a flagged one-off exception, not a 5th variant.
3. **New "Get a magic link" secondary sign-in path**, added directly below the Google button behind an "or" divider, from a screenshot reference David provided: a heading, description copy, an email `Field`, and a "Send magic link" `Button`. Reuses the existing `Field`/`Button` atoms — no new tokens.
4. **New Verify Email screen** (`/verify-email`, new route in `App.tsx`), the second step of the magic-link path: shows the email address passed via router state, a 4-digit one-time-code input (4 separate boxes, auto-advance focus on digit entry, backspace-to-previous), and a "Confirm code" button disabled until all 4 digits are filled. Since this repo is mock-data-only, **any** complete 4-digit code confirms — documented in the component's own comment as the intentional mock behavior, not a bug. Confirming is what actually flips `AuthContext.isAuthenticated`; the magic-link *send* step alone does not authenticate (Google SSO still does, on its own delay, mirroring how a real OAuth redirect already verifies identity before returning).
5. **Loading states added to `Button`** — a new `loading` prop (spinner replaces the label, `disabled` + `aria-busy` set, label kept for screen readers via a visually-hidden span) — the first async-feedback pattern in this repo, extending the atom rather than inventing a one-off. Wired to both the Google button (custom-styled, so it has its own parallel spinner CSS) and the magic-link Send/Confirm buttons, each behind a short fake delay (`setTimeout`, 700–900ms) so the loading state is actually visible — this repo has no real backend, so there is nothing real to wait on; the delay exists purely to make the mock experience readable.
6. **Two real bugs found and fixed**:
   - **Select fields rendered a boxed, wrong-font "Choose one" placeholder** (reported with a screenshot on the Sex/Education Level fields). Root cause: `Field.module.css`'s shared input-reset rule (`border: none; outline: none; background: transparent; font-family; color; padding`) only ever targeted the `input` element, never `select` — so a `<select>` inside the shared `field` container kept its full native browser chrome underneath the custom container border, producing a visible double-box artifact and default-font text. Fixed by extending every one of those shared selectors to also match `select`, in `Field.module.css` (not duplicated into `Select.module.css`, since `Select` already composes `Field`'s classes).
   - **A genuine flexbox layout bug** while building the split-screen Login (see below): a `flex: 1` panel with its own padding rendered visibly wider than its `flex: 1` sibling (768px vs. 672px of a 1440px row, not the expected 720/720) *despite* `box-sizing: border-box` being set on it — confirmed live via `getBoundingClientRect()`, isolated by testing with padding zeroed out (fixed it) and by moving the padding one layer in instead. Root-caused to how this browser engine resolves a percentage `flex-basis` (what the `flex: 1` shorthand expands to) against a padded item; the robust fix, independent of the underlying cause, is to never put padding directly on a `flex: 1` item with `flex-basis: 0` — put it on an inner, non-flex-item wrapper instead. Applied to both `LoginPage` and `VerifyEmailPage`.
7. **Login and Verify Email content polish**, all direct instructions: heading shortened from "Log in to Linus" to "Log in"; the subtitle paragraph under it removed entirely; "Get a magic link" changed from `<h2>` to `<h3>` — which on its own breaks the page's heading order (h1 → h3, skipping h2) and failed the existing `vitest-axe` accessibility test, so a visually-hidden `<h2>Sign in options</h2>` was added right after the `<h1>` to keep heading levels sequential for screen readers without introducing a second *visible* heading. This was a judgment call made without asking, since it's mechanical accessible-markup work the CLAUDE.md secure/accessible-coding default already covers, not a product decision.
8. **Login split into a 50/50 two-panel layout**, at David's request: a left panel with the existing sign-in content (now explicitly left-aligned, not centered) and a right panel reserved for a real photo/illustration — no asset exists yet, so it's a placeholder gradient (`primary-soft` → `secondary-subtle`, both existing tokens), clearly commented as reserved, not a broken image. Hidden below the `desktop` breakpoint (1280px, from `docs/design.md`'s `breakpoints` token) — below that, the form panel alone fills the screen, matching how every other screen in this prototype already behaves on mobile. `VerifyEmailPage` was then given the identical layout on request, so the two screens in the magic-link flow read as one continuous experience.
